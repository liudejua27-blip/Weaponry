`forgecad-runtime-contracts@1` is the only contract set used by the MCP002 Runtime
reset, MCP004 transaction core, and MCP005 reference admission. The manifest is the
checked-in source list; its schema count is derived from the files and is not a
capability claim. Rust owns runtime structs and SQLite read/write boundaries; these
JSON Schemas are reviewable interchange contracts, not a second product database.

## AuthoringMesh transaction family

The bounded multi-operation authoring journal is exposed as four closed contracts:

- `AuthoringMeshTransaction@1` (`authoring-mesh-transaction.schema.json`) is an
  ordered, hash-bound command journal. Its only operations are the currently
  implemented `split_edge`, `move_vertices`, and `face_extrude`; references are
  stable authored IDs or IDs generated by an earlier command in the same journal.
- `AuthoringMeshTransactionPrepareRequest@1` accepts only `project_id`, the journal,
  idempotency and response/hash policy fields. It intentionally does not carry raw
  mesh data, paths, scripts, candidate promotion, approval or source evidence.
- `AuthoringMeshTransactionGetRequest@1` is read-only and binds the transaction
  object/hash, mesh lineage, base revision and expected final/readback hashes.
- `AuthoringMeshTransactionResult@1` returns a complete ordered revision/step chain,
  immutable element deltas, Store/CAS commit status and strict topology/readback
  hashes. It never confirms a candidate, advances Stage, creates a version or exports.

Kernel, Store and MCP failures are typed `RuntimeError` values; no partial revision
chain is exposed. A successful result is structural/readback evidence only and does
not imply visual or commercial quality.

MCP003 exposes Runtime discovery and read-only inspection through the MCP stdio
adapter. MCP004 adds typed candidate/approval/restore/diagnostic-export transaction records behind
authenticated local IPC; MCP005 adds bounded PNG/JPEG reference admission and
hash-bound `ReferenceEvidence` readback. Geometry, rendering, materials and Skill
execution remain unavailable until each has a constrained operator, validator,
receipt and benchmark.

## Weaponry knife Tool profile

`profiles/weaponry-knife-tool-profile.schema.json` and
`profiles/weaponry-knife-p0.json` define the development-only knife profile as
one closed manifest rather than eleven new operation families. The default
Codex surface has exactly these façades:

`weapon_preflight`, `reference_intake`, `observe`, `authoring_transaction`,
`surface_pipeline`, `fps_presentation`, `quality_review`, `delivery`,
`approval`, `recovery`, and `job`.

Each façade binds explicit read/write route lists, a sorted underlying-operation
allowlist and its SHA-256. `scripts/check_weaponry_knife_profile.py` checks
those routes against the current source MCP manifest, rejects unknown or
misclassified routes, and exercises negative cases for open fields, stale
hashes and legacy-surface confusion. The explicit compatibility profile binds
the complete 131-read/95-write/226-total legacy manifest and its manifest hashes;
it does not masquerade as the default eleven-façade surface. The profile files
are registered separately from the legacy source-tool manifest, so the native
operations below do not alter the 226-route source truth or historical evidence.

## Delivery request closure

The Delivery domain has eleven active operations: four reads and seven writes. `version_diff`
already exposes a closed request shape in the active MCP profile. The other ten operations now
have closed, checked-in request contracts in this package:

| Active operation | Request contract | Field source |
| --- | --- | --- |
| `game_asset_delivery_get` | `game-asset-delivery-get-request.schema.json` | `game_asset_delivery::get` exact object |
| `game_asset_delivery_prepare` | `game-asset-delivery-prepare-request.schema.json` | `game_asset_delivery::prepare` exact object |
| `game_asset_lod_derive` | `game-asset-lod-derive-request.schema.json` | `game_asset_delivery::derive_lods` exact object |
| `game_weapon_glb_socket_get` | `game-weapon-glb-socket-materialization-get-request.schema.json` | `weapon_glb_socket_get` exact object |
| `game_weapon_glb_socket_prepare` | `game-weapon-glb-socket-materialization-prepare-request.schema.json` | `weapon_glb_socket_prepare` exact object |
| `candidate_confirm` | `candidate-confirm-request.schema.json` | `CandidateConfirmRequest` + Store validator |
| `candidate_reject` | `candidate-reject-request.schema.json` | `CandidateRejectRequest` + Store validator |
| `cross_view_promotion_confirm` | `cross-view-promotion-request.schema.json` | `CrossViewPromotionRequest` + Runtime key validator |
| `export_prepare` | `export-prepare-request.schema.json` | `ExportPrepareRequest` + Store validator |
| `export_confirm` | `export-confirm-request.schema.json` | `ExportConfirmRequest` + Store validator |

Each outer request object rejects unknown fields. `base_version_id` remains an optional nullable
identifier where the Rust `Option<String>` accepts omission or `null`; the export `request` member
remains an object without an invented property allowlist because Runtime currently accepts its
typed export options as a `serde_json::Value`. This keeps the request boundary closed without
silently narrowing the Runtime action space. The four approval/export schemas added in this
closure bring the package manifest and schema directory to the same 593-file set; they do not by
themselves change the active MCP adapter's operation-schema consumer or imply visual, engine, or
commercial acceptance.

## Knife curve EvaluatedMesh façade

The façade-native `knife_curve_evaluated_mesh_prepare` / `knife_curve_evaluated_mesh_get`
operations are registered in the profile and core contract manifest, but deliberately do not
enter the legacy MCP read/write tool manifest. They are the next typed slice after the
structural `KnifeCurveModifierGraph*@1` replay contracts; those older contracts remain
unchanged compatibility records.

The exact Runtime alignment fields are:

| Contract | Required binding fields |
| --- | --- |
| `KnifeCurveEvaluatedMeshPrepareRequest@1` | `project_id`, `source_candidate_id`, `source_candidate_state_sha256`, `source_authoring_mesh_id`, `source_authoring_mesh_lineage_id`, `source_authoring_mesh_revision_id`, `source_authoring_mesh_revision_index`, `source_authoring_mesh_revision_sha256`, `source_authoring_mesh_identity_sha256`, `source_modifier_graph_id`, `source_modifier_graph_sha256`, five source semantic hashes (`curve_set_semantic_sha256`, `sample_set_semantic_sha256`, `modifier_graph_semantic_sha256`, `dependency_graph_semantic_sha256`, `recompute_plan_semantic_sha256`), `curve_graph_lookup_key_sha256`, and `evaluation_plan` |
| `KnifeBladeProfileSweepLoftPlan@1` | `evaluation_id`, `spine_curve_id` + `spine_curve_sha256`, `edge_curve_id` + `edge_curve_sha256`, fixed `station_count=32`, `thickness_axis` in `local_normal / world_x / world_y / world_z`, bounded `thickness_m` (`0.0001 < thickness_m <= 0.25`), `root_cap=true`, `tip_cap=true`, `stable_triangulation=station-ring-fixed-diagonal@1`, `stable_lineage_policy=source-curve-modifier-graph-evaluated-mesh@1`, and `canonical_sha256` |
| `KnifeCurveEvaluatedMeshResult@1` | The complete source binding and plan above, `evaluation_plan_object_sha256`, `evaluation_plan_semantic_sha256`, Runtime-derived `evaluated_mesh_id`, `evaluated_mesh_object_sha256`, `evaluated_mesh_semantic_sha256`, `evaluated_mesh_identity_sha256`, `evaluated_mesh_link_sha256`, `evaluated_mesh_lookup_key_sha256`, `vertex_count`, `triangle_count`, `closed_two_manifold=true`, `zero_degenerate_triangles=true`, strict readback/replay and Store/CAS atomicity fields |
| `KnifeCurveEvaluatedMeshGetRequest@1` | The complete source identity and five semantic hashes, `evaluated_mesh_lookup_key_sha256`, exact evaluation-plan object/semantic hashes, `evaluated_mesh_id`, object/semantic/identity/link hashes, and exact vertex/triangle counts; `runtime_write_performed=false` |

The result truth is intentionally narrow: `evaluated_mesh_created=true` while
`geometry_artifact_created=false`; `high_status`, `uv_status`, `bake_status`, `visual_status`,
`human_status`, and `engine_status` are all `NOT_RUN`. The evaluated mesh is a disposable
sidecar: callers receive no evaluated lineage/revision identity that could become a second
editable source of truth. `source_authoring_mesh_revision_sha256` and
`source_modifier_graph_sha256` remain the real AuthoringMesh revision and ModifierGraph
bindings used to derive the EvaluatedMesh identity/link hashes. No raw vertices/faces, path,
URL, script, or arbitrary executor is representable.

Run the independent positive/negative contract gate with:

```bash
python3 scripts/check_knife_curve_evaluated_mesh_contract.py
```
